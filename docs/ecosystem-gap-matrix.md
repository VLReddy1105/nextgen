## Implementation sequence and verification

Follow requested stages: shared design/forms → relationship/invitation foundation → project policies → Company lifecycle → University membership/content/privacy → Mentor → communities → Student profile/review → shared notifications/consistency → responsive checks → full test/build suite. Each migration is tested against all historical migrations in the isolated PostgreSQL harness. Auth regression, permission/negative cases and cross-role state transitions are required before reporting completion. No live users or production fixture data will be created.

Domain ownership cannot safely be proved by allowing a university manager to type any domain. A verified university can request/configure a domain, but platform approval of that exact domain is required before matching enables membership flows. Auto-enrollment additionally requires an explicit Student confirmation and the university's enabled policy. This preserves existing institutional verification authority.

The staged implementation and verification results are recorded in [ecosystem-implementation-report.md](ecosystem-implementation-report.md). Seven additive migrations implement the new relationship and cross-role behavior; all 16 pre-existing migration hashes remain unchanged. Hosted migration application and real-account acceptance are still separate deployment checks.
